## 1. Цель и постановка задачи W6

Практическая работа Week 6 посвящена архитектуре аккаунтов Solana и **Program Derived Addresses (PDA)**. Требовалось реализовать простую программу, которая сохраняет профиль пользователя в on-chain аккаунте, связывает профиль с публичным ключом владельца и разрешает изменение только этому владельцу.

**Поставленные требования:**

1. Создать минимальную on-chain программу на **Rust + Anchor**, без избыточных функций и зависимостей.
2. Вычислять адрес профиля (**PDA**) детерминированно на основе seeds, содержащих идентификатор пользователя (его wallet public key), и идентификатора программы.
3. Реализовать инструкцию `initialize_profile`, создающую аккаунт профиля.
4. Реализовать инструкцию `update_profile`, позволяющую изменять профиль **только авторизованному владельцу**.
5. Подготовить **TypeScript-клиент**, демонстрирующий создание, изменение и чтение профиля.
6. Проверить положительные и отрицательные сценарии, в том числе попытку изменения данных чужим кошельком и проверку ограничения длины данных.
7. Собрать программу и проверить функциональность в **localnet** либо Devnet, не обращаясь к Mainnet.

**Ожидаемый результат:** воспроизводимый минимальный пример того, как Solana-программа работает с состоянием пользователя, PDA и авторизацией, а TypeScript-клиент взаимодействует с этой программой.

## 2. Теоретическая основа и архитектура

### 2.1. Почему нужен PDA

В Solana состояние приложения хранится в аккаунтах. Обычный кошелёк пользователя определяется ключевой парой, но аккаунт состояния программы удобнее привязать к **PDA — адресу, выводимому из набора seeds и Program ID**. Адрес PDA можно вычислить повторно, не создавая для него отдельный обычный приватный ключ.

В W6 предполагалась логическая связь:

```text
Wallet public key (владелец)
        |
        | + seed(s) + Program ID
        v
PDA профиля пользователя
        |
        | accounts / instructions
        v
Anchor program (Rust)
   |-- initialize_profile
   +-- update_profile (только владелец)
        ^
        |
TypeScript client -> создание, обновление, чтение
```

Важны два разных свойства: **детерминированность адреса** (клиент может найти профиль по кошельку) и **контроль прав** (знание адреса PDA само по себе не даёт права изменять данные). Конкретная строка seed, структура полей и ограничения аккаунтов должны проверяться по исходному коду W6; их точный вид не выводится из одного текстового журнала.

### 2.2. Сценарии работы

**Создание профиля:**
- Клиент подключается к локальной сети и выбирает кошелёк, который будет владельцем.
- Клиент и программа используют согласованные seeds для PDA.
- Вызов `initialize_profile` должен инициализировать аккаунт профиля и записать начальные данные.
- После подтверждения транзакции профиль можно найти по PDA и прочитать.

**Обновление профиля:**
- Владелец отправляет `update_profile` с новыми данными.
- Программа должна проверить авторизацию инициатора и допустимость обновления.
- Авторизованное обновление сохраняется в on-chain аккаунте; последующее чтение возвращает новое состояние.

**Попытка постороннего изменения:**
- Иной кошелёк пытается изменить профиль владельца.
- Ожидаемый результат — отказ программы и отсутствие несанкционированного изменения состояния.

Это описание требований и предполагаемого поведения, **не дословная расшифровка отсутствующего в GitHub кода**.

## 6. Безопасность и ограничения

При выполнении работы использовались следующие правила:

- **Не использовать Mainnet** для учебной разработки; W6 проверялся локально.
- Не публиковать seed-фразы, приватные ключи, содержимое секретного wallet JSON или Helius API-ключ.
- Не подменять проверку авторизации одним лишь вычислением адреса PDA: `update_profile` должен контролировать права на запись.
- Проверять недопустимые значения данных, в том числе ограничение длины профиля.
- Не запускать сетевые транзакции без предварительной проверки кластера и необходимости действия.

По записи подготовки архива, в `W6-submission.zip` **нет приватных ключей**. Однако этот архив в текущем GitHub не размещён и здесь **не проверялся повторно**; перед дальнейшей публикацией или отправкой преподавателю рекомендуется проверить содержимое на secrets.

**Helius Devnet RPC** остался ненастроенным: требовалось передать приватный RPC URL локально (например, через переменную окружения `HELIUS_RPC_URL`). # Практика Solana на лекции

Источник: https://github.com/0xnurda/solana-practice
Выполнено 12.10.2026 в Devnet. Перевод 0.01 SOL с memo, mint 10000, три перевода по 100 и burn 50 подтверждены. Балансы: 9650 у отправителя, по 100 у трёх собственных тестовых получателей; supply 9950. Собственные получатели использованы с разрешения преподавателя, подтверждённого пользователем.

Задачи по исходному коду:
- dev: перевод 0.01 Devnet SOL с memo Hello Solana на случайный публичный адрес.
- mint: выпуск 10000 SPL-токенов с decimals 6, отправка 3 однокурсникам по 100, burn 50.
- После mint: баланс отправителя 9650, supply 9950.

Исправления: удалён вывод приватного ключа; Devnet проверяется по genesis hash; адреса и кошелёк валидируются до mint; ошибки не раскрывают ключи. Название MYCOIN используется в сообщениях, on-chain metadata исходный код не создаёт.

Запуск в Ubuntu:

```bash
npm ci
npx tsc --noEmit
# WALLET_PATH: отдельный Devnet JSON-кошелёк вне репозитория.
# Или ENV_FILE: путь к приватной конфигурации вне репозитория.
# RECIPIENT_1, RECIPIENT_2, RECIPIENT_3: три публичных адреса однокурсников.
npm run dev
npm run mint
```

Не использовать локальные ключи W6 для Devnet. Не размещать SECRET_KEY, JSON-ключи и seed-фразы внутри проекта. Не запускать mint повторно без проверки результата предыдущего запуска.

Подтверждения: transfer-result.txt, mint-result.txt, balances.json. Все операции завершены; повторный запуск создаст новый токен и повторит операции.
